## Intro

앞선 글에서 DEDALE 로그를 Elasticsearch에 넣고, Qwen이 MCP를 통해 검색할 수 있는 환경을 만들었습니다.

이번에는 프로젝트의 핵심인 **자동 조사 하네스**를 구현했습니다. Sigma가 Alert를 만들면 Local LLM이 관련 로그를 조회하고, 분석이 부족하면 다시 검색한 뒤, 마지막에 HTML 보고서를 작성하는 구조입니다.

```text
Sigma Alert
   ↓
관련 로그 조회 → 분석 → 추가 조회 필요?
   ↑                     │
   └──── Yes ─────┘
                         ↓ No
                   HTML 보고서
```

시스템 프롬프트만 길게 작성해서는 반복 횟수와 종료 조건을 안정적으로 제어하기 어려웠습니다. 그래서 Python 코드가 전체 순서를 관리하고, Qwen은 각 단계에서 조회 계획과 분석 결과를 만들도록 역할을 나눴습니다.
<br><br>

## 00_Sigma Alert 형식 정하기

팀원이 만든 Sigma 탐지 결과가 LLM으로 넘어오려면 공통 형식이 필요합니다. 너무 많은 원본 필드를 모두 보내기보다, 조사 시작에 필요한 값과 원본 이벤트를 다시 찾을 수 있는 식별자를 남겼습니다.

```json
{
  "alert_id": "alert-20250106-100105-001",
  "detected_at": "2025-01-06T10:01:05Z",
  "rule": {
    "id": "sigma-rule-id",
    "title": "Suspicious Command Execution",
    "level": "high"
  },
  "event": {
    "index": "dedale-winlogbeat-6pc-5h-20250106",
    "document_id": "elasticsearch-document-id",
    "timestamp": "2025-01-06T10:01:05Z",
    "host": "CLIENT2.breach.local",
    "event_code": "1"
  },
  "matched_on": {
    "process.command_line": "...",
    "process.executable": "..."
  }
}
```

`rule`에는 어떤 조건에서 잡혔는지를, `event`에는 Elasticsearch의 원본 문서를 다시 찾을 값을 넣었습니다. `matched_on`은 룰과 일치한 핵심 필드만 담습니다.

Alert는 결론이 아닙니다. `level`이 high라고 해서 보고서도 무조건 악성으로 판단하지 않습니다. LLM은 원본 문서와 주변 로그를 확인한 뒤 별도의 결론을 내려야 합니다.
<br><br>

## 01_조사 하네스 구조

하네스는 조회와 분석을 **최대 10단계**까지 반복합니다.

여기서 10회는 MCP 도구를 딱 10번만 호출한다는 뜻이 아닙니다. 하나의 조사 단계 안에서는 여러 Elasticsearch 쿼리를 사용할 수 있고, ‘조회 결과를 보고 다음 조사로 넘어가는 판단’의 횟수만 제한합니다.

```text
1단계: Alert 원본 문서 확인 + 초기 Pivot
   ↓
2단계: 조회 결과 분석 + 다음 검색 계획
   ↓
3단계: 추가 로그 조회 + 가설 갱신
   ↓
...
   ↓
최대 10단계 또는 충분한 근거 확보
   ↓
최종 판단 및 보고서
```

### 01-1_첫 단계는 고정 조회

첫 단계에서는 모델의 선택에만 의존하지 않습니다. Alert가 가리키는 Elasticsearch 문서를 ID로 정확히 가져오고, 같은 호스트·인접 시간대의 이벤트를 함께 조회합니다.

파일 경로와 IP가 있다면 해당 값도 초기 Pivot으로 사용합니다. 덕분에 모델이 시작부터 엉뚱한 인덱스나 시간대를 검색하는 일을 줄였습니다.

### 01-2_이후 단계는 계획과 실행을 분리

Qwen은 현재까지의 증거를 읽고 다음 질문을 만듭니다. 예를 들면 ‘이 프로세스를 만든 부모 프로세스가 있는가?’, ‘생성된 파일이 이후 실행됐는가?’와 같은 질문입니다.

하네스는 그 질문을 허용된 Elasticsearch 검색으로 바꾸어 실행합니다. 조회 결과는 다시 모델에 전달되고, 모델은 가설을 유지할지 수정할지 결정합니다.

### 01-3_종료 조건

다음 중 하나를 만족하면 조사를 끝냅니다.

- 악성 또는 정상 판단에 필요한 근거가 충분함
- 추가 검색 항목이 없음
- 같은 쿼리와 결과가 반복됨
- 최대 10단계에 도달함
- Elasticsearch 또는 모델 호출 오류가 복구되지 않음

무한 반복을 막는 것뿐 아니라, 왜 중단됐는지도 보고서에 남기도록 했습니다.

## 02_명령 실행과 결과를 구분하기

로그 분석에서 가장 조심한 부분은 **명령이 보인다는 것과 결과가 성공했다는 것을 구분하는 일**이었습니다.

예를 들어 다운로드 명령이 실행됐다고 해서 파일을 실제로 받았다고 단정할 수는 없습니다. 이어지는 파일 생성이나 네트워크 연결 로그가 있어야 성공 여부를 더 강하게 말할 수 있습니다.

그래서 최종 판단에는 다음 원칙을 적용했습니다.

1. 관찰된 로그만 사실로 작성한다.
2. 명령 문자열은 ‘시도’의 증거로 본다.
3. 파일 생성·프로세스 실행·네트워크 연결은 각각 별도 이벤트로 확인한다.
4. 확인되지 않은 결과는 ‘미확인’으로 남긴다.
5. Ground Truth는 분석 입력으로 사용하지 않는다.

LLM이 자연스러운 문장을 만드는 것보다, **확인한 범위와 확인하지 못한 범위의 경계**를 지키는 것이 더 중요했습니다.
<br><br>

## 03_5시간 로그 재생과 Alert 전달

실시간 로그 수집기가 없어도 전체 흐름을 시험할 수 있도록 Python 기반 Replay Detector를 만들었습니다. 저장된 5시간 로그를 시간 순서로 읽고, 임시 Sigma 룰과 일치한 이벤트를 Alert 형식으로 바꾼 뒤 조사 하네스를 실행합니다.

실행 모드는 세 가지로 나눴습니다.

| 실행 방법 | 동작 |
|---|---|
| 기본 실행 | 5시간 시간축을 재생하고 Alert 발생 시 Qwen 조사 및 보고서 작성 |
| `--siem` | 룰 탐지만 수행하고 Alert·일치 로그를 확인 |
| `--speed` | 시간 대기 없이 탐지된 이벤트를 바로 조사 |

```bash
python3 sigma_replay_detector.py
python3 sigma_replay_detector.py --siem
python3 sigma_replay_detector.py --speed
```

`--speed` 시험에서는 룰과 일치한 원본 로그 7건이 나왔고, 같은 사건을 묶어 2개의 Alert로 정리했습니다. 이후 두 Alert 모두 조사와 보고서 생성까지 완료했습니다.

```json
{
  "mode": "speed",
  "raw_matching_logs": 7,
  "grouped_alerts": 2,
  "investigations_done": 2
}
```

다만 이 수치는 전체 악성 행위에 대한 탐지율이 아닙니다. 파이프라인을 연결하기 위한 **임시 시험 룰의 결과**이므로, 실제 Sigma 룰 성능과는 분리해서 봐야 합니다.

DEDALE 필드의 대소문자 차이로 문자열 조건이 빠지는 문제도 있었습니다. 탐지 비교를 대소문자 무시 방식으로 통일해 `PowerShell`, `powershell`, `POWERSHELL`이 같은 값으로 처리되도록 수정했습니다.

## 04_HTML 보고서 만들기

조사가 끝나면 Qwen은 정해진 JSON 구조로 분석 내용을 반환합니다. Python은 이 값을 HTML 템플릿에 넣고 특수 문자를 안전하게 처리합니다.

모델이 HTML 전체를 직접 작성하지 않게 한 이유는 출력 형식이 매번 달라지거나, 로그 문자열이 태그로 해석되는 문제를 막기 위해서입니다.

보고서 파일명에는 최초 Alert 이벤트의 시각을 사용합니다.

```text
2025-01-06_10-01-05.html
```

![Qwen이 DEDALE 악성 이벤트를 분석해 생성한 HTML 보고서](/img/posts/siem-project-report.png)

보고서는 흑백과 회색을 사용해 다음 항목을 한 화면에서 확인할 수 있도록 구성했습니다.

- 사건 요약과 최종 판단
- 주요 이벤트 타임라인
- 최초 Sigma Alert
- 판단 근거가 된 Elasticsearch 문서
- 확인하지 못한 제한 사항
- 보안 담당자에게 권장하는 다음 조치

각 근거에는 시각, 호스트, 이벤트 코드, Elasticsearch 문서 ID를 함께 넣었습니다. 담당자가 자연어 설명만 믿지 않고 원본 로그를 다시 찾을 수 있게 하기 위해서입니다.

## 05_실제 로그 검증

하네스가 무조건 Alert를 악성으로 판단하지 않는지 확인하기 위해 침해 호스트와 정상 호스트를 각각 시험했습니다.

### 05-1_CLIENT2 침해 사례

CLIENT2에서는 10:01:05 UTC의 명령 실행을 시작점으로 조사했습니다. 주변 Sysmon 로그를 따라가자 다음 흐름이 확인됐습니다.

| 시각(UTC) | Event ID | 관찰 내용 |
|---|---:|---|
| 10:01:05 | - | 의심 명령 실행 |
| 10:01:13 | 11 | `tmp.zip` 파일 생성 |
| 10:03:04 | 11 | `scvhost.exe` 파일 생성 |
| 10:03:44 | 1 | `scvhost.exe` 프로세스 실행 |
| 10:04:50 | 5 | 해당 프로세스 종료 |

명령 실행 뒤 파일이 생성되고, 이어서 실행된 흐름이 연결됐기 때문에 보고서는 **True Positive**로 판단했습니다.

다만 명령에 포함된 `172.19.1.1` 대상의 Sysmon Event ID 3은 찾지 못했습니다. 따라서 네트워크 연결이나 다운로드 성공 자체는 확인할 수 없다고 제한 사항에 남겼습니다.

### 05-2_CLIENT3 정상 사례

정상 호스트인 CLIENT3의 프로세스 생성 Alert도 같은 방식으로 조사했습니다. 주변에는 Python multiprocessing, Windows Search, Prefetch 관련 이벤트가 이어졌고 침해를 뒷받침할 파일·통신 흐름은 없었습니다.

이 사례는 **False Positive**로 정리됐습니다. 같은 조사 구조라도 호스트와 주변 로그가 다르면 다른 결론을 낼 수 있다는 것을 확인했습니다.

초기 버전에서는 모델이 룰 이름에 포함된 `synthetic smoke rule`이라는 표현을 정상 근거처럼 사용하기도 했습니다. 룰 이름은 시험용이라는 설명일 뿐 실제 정상 행위의 증거가 아닙니다. 이후 `test`, `smoke`, `synthetic` 같은 메타 표현을 증거로 채택하지 못하도록 검증 단계를 추가했습니다.

## 06_테스트와 한계

조사 하네스 14개, 로그 재생 및 보고서 9개로 총 **23개의 자동 테스트**를 구성했습니다.

테스트에서는 다음을 확인합니다.

- Alert JSON 필수 필드 검증
- Elasticsearch 원본 문서 조회
- 최대 10단계 제한
- 중복 쿼리 및 반복 결과 중단
- 정상·악성 판단 값 검증
- HTML 특수 문자 처리
- 파일명과 타임스탬프 일치
- Ground Truth 입력 차단
- Sigma 문자열 대소문자 무시

가장 큰 현실적인 한계는 속도입니다. CPU에서 27B 모델을 실행하면 Alert 한 건을 조사하는 데 약 3~8분이 걸렸습니다. 짧은 데모에는 사용할 수 있지만 많은 Alert를 동시에 처리하려면 GPU, 더 작은 모델, 조사 우선순위와 큐가 필요합니다.

또 현재 사용한 Sigma 룰은 파이프라인 검증용입니다. 전체 432개의 악성·관련 정답 이벤트를 모두 탐지하도록 설계한 룰셋은 아니므로, 프로젝트의 탐지 성능은 팀원의 실제 룰을 연결한 뒤 별도로 평가해야 합니다.

## 07_RAG는 필요한가

로그 전체를 Vector DB에 넣는 RAG도 고민했지만, 현재 구조에서는 Elasticsearch가 더 적합했습니다.

보안 로그 조사는 정확한 시간, 호스트, Event ID, 파일 해시처럼 **일치 조건과 범위 검색**이 중요합니다. 이미 Elasticsearch가 이 역할을 잘 수행하고 있기 때문에 같은 로그를 다시 임베딩하면 저장 공간과 동기화 문제만 늘어날 수 있습니다.

대신 추후 아래와 같은 정적 지식에는 작은 RAG를 붙일 수 있습니다.

- Sigma 룰 설명과 튜닝 기록
- Sysmon Event ID 해설
- MITRE ATT&CK 기법 정보
- 조직의 자산·계정 정보
- 과거 분석 보고서와 대응 절차

정리하면 **이벤트는 Elasticsearch에서 검색하고, 지식 문서는 RAG에서 찾는 구조**가 더 자연스럽다고 판단했습니다.

## 08_Outro

이번 단계에서는 Alert 한 건을 받아 원본 로그를 찾고, 관련 이벤트를 반복 조회한 뒤, 근거가 남는 HTML 보고서로 만드는 전체 흐름을 연결했습니다.

구현하면서 느낀 점은 LLM의 문장보다 하네스의 경계가 더 중요하다는 것입니다. 조회 횟수, 허용 도구, 종료 조건, Ground Truth 분리, 근거 ID를 코드에서 강제해야 결과를 다시 검증할 수 있었습니다.

아직 탐지 룰 확대와 처리 속도 개선이 남아 있습니다. 이후에는 팀원이 만든 실제 Sigma 룰을 연결하고, 432개의 정답 이벤트와 비교해 탐지·분석 성능을 각각 평가해보려고 합니다.
