## 00_Intro

안녕하세요! 이번에는 **CVE-2026-109618**, 이른바 **php2shell**을 분석해보겠습니다.

php2shell은 PHP 엔진에서 발견된 두 취약점, CVE-2026-109618과 CVE-2026-109619를 함께 부르는 이름입니다. 이 글에서 다루는 것은 **메모리 부족(OOM) 이후의 상태 손상**을 이용하는 CVE-2026-109618입니다. [PHP 공식 보안 권고](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w)는 Apache mod_php 환경에서 인증 없이 웹 작업자 권한으로 원격 코드를 실행할 수 있음을 확인했습니다.

평범한 PHP 웹사이트가 어떻게 이런 문제에 노출되는지, 요청의 시작과 끝을 따라가며 살펴보겠습니다. 마지막에는 제가 만든 [로컬 실습 저장소](https://github.com/amier-ge/php2shell)의 쇼핑몰에서 익스플로잇을 실행하고, `www-data` 셸까지 연결되는 데모를 보여드리겠습니다.

## 01_취약점 원인 분석

### 01-1_PHP는 페이지 코드보다 먼저 요청을 처리한다

브라우저가 `index.php`에 요청을 보내면, PHP는 바로 페이지의 첫 줄부터 실행하지 않습니다. 먼저 요청 본문을 읽고, 폼 데이터를 해석하고, 실행에 필요한 내부 상태를 준비합니다. 따라서 페이지 코드에 특별한 취약점이 없어도 **PHP의 입력 처리 단계**가 공격 표면이 될 수 있습니다.

이번 문제는 그 준비 과정에서 메모리가 부족해졌을 때 드러납니다. PHP는 OOM을 만나면 `longjmp()`로 현재 작업을 빠져나가 요청 처리를 중단합니다. 그런데 일부 내부 객체는 **초기화가 끝나기 전에 다른 코드에서 접근 가능한 상태**가 됩니다. 이 시점에 중단되면 정리 코드가 미완성 상태를 정상적인 상태처럼 읽을 수 있습니다. [[PHP 공식 원인 설명]](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w)

```text
HTTP 요청 → PHP의 입력 해석 → 메모리 부족
                           ↓
                    longjmp()로 작업 중단
                           ↓
               미완성 내부 상태가 남은 채 요청 종료
                           ↓
                  정리 과정에서 잘못된 상태 참조
```
<br>

핵심은 단순히 “큰 요청을 보내 서버를 느리게 만든다”가 아닙니다. **중단된 위치와 정리 순서가 맞물려 메모리 상태가 손상되는 것**이 문제입니다. 공식 권고는 mod_php가 요청 시작에 실패해도 종료 절차를 수행하며, 그 과정에서 잘못된 상태를 소비할 수 있다고 설명합니다. 이 흐름은 애플리케이션 코드가 실행되기 전에도 성립할 수 있습니다.

### 01-2_왜 RCE까지 이어질 수 있는가?

잘못된 메모리 참조가 항상 코드 실행으로 이어지지는 않습니다. 공격자는 어느 메모리가 다시 쓰이는지, 종료 코드가 그 내용을 어떤 자료구조로 해석하는지까지 맞춰야 합니다. 조건이 맞으면 정리 코드가 공격자가 의도한 값을 PHP의 내부 포인터나 함수 호출 정보로 받아들일 수 있습니다.

PHP는 변수의 값과 타입을 `zval`로, 배열은 `HashTable`로 관리합니다. 데모에서는 입력을 여러 번 교체해 메모리 재사용을 유도하고, 종료 처리 때 재사용된 영역이 이런 내부 구조처럼 읽히는 상황을 만듭니다. **OOM은 시작점이고, 잘못된 자료구조 해석이 코드 실행으로 이어지는 연결 고리**입니다.

여기서 `RCE(Remote Code Execution)`는 외부 요청만으로 서버 프로세스 안에서 명령을 실행한다는 뜻입니다. <br>공식 권고가 확인한 실행 권한은 웹 작업자 계정이며, 곧바로 서버의 `root` 권한을 얻는다는 의미는 아닙니다. 데모에서도 명령은 `www-data`로 실행됩니다. [[영향 범위]](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w)

### 01-3_이 익스플로잇에 필요한 주소와 ASLR leak

이 데모의 익스플로잇 요청에는 **힙 청크 주소와 libc의 `system()` 주소**가 들어갑니다. ASLR은 프로세스마다 이런 주소를 바꾸므로, 이전 실행에서 얻은 값을 그대로 넣어서는 안정적으로 명령을 실행할 수 없습니다.

따라서 같은 방식을 원격 서버에 적용하려면, 공격자가 이용할 수 있는 **ASLR leak으로 실행 중인 주소를 알아내거나 동등한 주소 우회 방법**이 필요합니다. 주소를 몰라도 OOM에 따른 메모리 손상은 일어날 수 있지만, 그것을 이 방식의 RCE로 이어 붙이기는 어렵습니다.

현재 제 데모는 ASLR leak을 구현하지 않았습니다. 대신 **로컬 GDB와 프로세스 메모리 맵**으로 실습 컨테이너의 주소를 직접 확인합니다. 즉, 셸 연결 결과는 로컬에서 주소를 알고 진행한 재현이며, 임의의 외부 서버를 HTTP 요청만으로 공격할 수 있다는 증명은 아닙니다.

## 02_공격이 성립하는 흐름

이 취약점에서 OOM은 출발점일 뿐입니다. 그 뒤에 남은 메모리 상태가 종료 처리에서 다시 사용되고, 공격자가 의도한 자료구조와 메모리 주소까지 맞아야 명령 실행으로 이어집니다. 공식 권고 역시 PHP 빌드, 확장 모듈, 웹서버와 메모리 배치에 따라 성공률이 달라진다고 설명합니다. [[PHP 공식 권고]](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w)

```text
입력 처리 중 OOM
    → 미완성 상태가 남음
    → 종료 처리에서 잘못된 자료구조를 읽음
    → 메모리 주소와 실행 흐름을 제어할 수 있다면 RCE
```

참고로! 여기서 셸은 취약점 자체의 이름이 아니라, **RCE가 성공했음을 확인하는 한 가지 방식**입니다. <br>같은 코드 실행 권한은 상황에 따라 파일 열람, 웹사이트 변조 등 다른 행위로도 이어질 수 있습니다. 제가 만든 로컬 데모가 이 조건을 어떻게 확인하는지는 뒤에서 보여드리겠습니다.

## 03_AI가 낮춘 문턱, 여전히 높은 난이도

한 기사에서는는 보안업체 Calif가 **GPT-5.6 Sol**을 활용해 PHP의 취약점을 찾아냈다고 전했습니다. [[FORTUNE KOREA]](https://www.fortunekorea.co.kr/news/articleView.html?idxno=54461) <br>[OpenAI의 공개 설명](https://openai.com/index/coordinated-disclosure-of-critical-vulnerabilities/)도 Calif의 AI 활용과 Wiz의 독립적인 발견, PHP 개발진의 수정 작업을 구분해 소개합니다.

AI 덕분에 방대한 소스 코드를 추적하고, 실패한 가설을 다시 시험하는 속도는 빨라졌습니다. 취약점 연구에 들어가는 **진입장벽이 낮아진 것**은 분명해 보입니다. 하지만 메모리 수명과 요청 처리 순서를 이해하고, 실제 실행 조건을 재현하며, ASLR 같은 제약까지 해결하는 일은 여전히 어렵습니다. AI가 단서를 빨리 찾아줘도, 그 단서가 실제 취약점인지 검증하고 안전한 패치로 연결하는 과정에는 깊은 전문성이 필요합니다.

## 04_패치와 대응

[PHP 공식 권고](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w)에 따르면 수정 버전은 **8.2.35, 8.3.36, 8.4.27, 8.5.12**입니다. 이번 패치는 OOM에서 무조건 `longjmp()`로 빠져나가던 방식을 바꾸고, 미완성 상태를 종료 처리 코드가 읽지 않도록 합니다.

운영 중인 서버라면 PHP 버전만 확인하는 데서 끝내지 말고, 실제 요청을 처리하는 Apache 또는 PHP-FPM 작업자가 수정된 바이너리로 재시작됐는지도 확인해야 합니다. 컨테이너를 사용한다면 이미지를 새로 빌드하거나 교체해야 합니다. **임시 설정 변경이나 WAF 규칙은 패치를 대신하지 못합니다.** 관련된 CVE-2026-109619도 함께 확인해야 합니다. [[CVE-2026-109619 공식 권고]](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp)

## 05_로컬 실습 환경

데모에 들어가기 전에 공격 대상을 구분해야 합니다. **Onda Living**은 상품 목록과 검색 기능을 가진 가상의 PHP 쇼핑몰입니다. 화면에는 별도의 명령 실행 기능이 없고, 검색어도 출력할 때 이스케이프합니다. 이번 취약점의 원인은 이 페이지의 비즈니스 로직이 아니라, 요청을 처리하는 **PHP 런타임 내부**에 있습니다.

| 구분 | 역할 | 데모에서의 의미 |
| --- | --- | --- |
| `website/` | 쇼핑몰 화면을 보여주는 PHP 파일과 CSS | 실제 사이트처럼 보이는 실습 대상 |
| PHP 8.2.6 + Apache mod_php | 취약점 재현용 디버그 환경 | `127.0.0.1:18085`에서 셸 연결 검증 |
| PHP 8.4.26 / 8.4.27 | 같은 페이지를 제공하는 취약판·패치판 | 버전 비교용 환경, 이 두 컨테이너에서 셸 획득을 검증한 것은 아님 |

<br>

즉, 스크린샷의 쇼핑몰은 **취약한 PHP로 실행한 웹사이트**입니다. 특정 쇼핑몰만의 버그를 이용했다는 뜻은 아닙니다. 다만 실제 서비스의 노출 여부와 익스플로잇 성공 가능성은 PHP 버전뿐 아니라 SAPI, 서버 설정, 확장 모듈, 메모리 배치에도 영향을 받습니다. [[PHP 공식 권고]](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w)

## 06_Exploit 데모

실습 파일은 `website/`와 `exploit/`으로 나누었습니다. `website/`에는 쇼핑몰 화면이 있고, `exploit/`에는 PHP 8.2.6 디버그 컨테이너, 주소 보정 코드, 요청 생성기, 셸 중계기가 있습니다. **`exp.py`만 복사해서 실행하는 구조는 아닙니다.** Docker Compose와 나머지 파일이 함께 있어야 합니다.

Windows PowerShell에서 프로젝트의 `php2shell` 폴더로 이동한 뒤 실행합니다. Docker와 Python 3.10 이상이 필요합니다.

```powershell
docker compose up -d
python .\exploit\exp.py
```
<br>

첫 번째 명령은 같은 쇼핑몰을 PHP 8.4.26과 8.4.27에서 각각 띄웁니다. 두 번째 명령은 별도의 PHP 8.2.6 디버그 환경을 시작해 셸 연결을 재현합니다. 사이트는 `http://127.0.0.1:18085/`, 비교용 환경은 `18080`과 `18081`에서 확인할 수 있습니다. 셸을 마치려면 `exit`를 입력하면 됩니다.

실행 화면의 `[+]` 메시지는 컨테이너 준비, GDB 보정, 요청 전송, 셸 검증 순서를 보여줍니다. 아래 화면에서는 `whoami`가 `www-data`를 반환하고, `ls`로 쇼핑몰 파일이 보입니다. **웹 작업자 권한으로 실제 명령이 실행된 것**을 확인할 수 있습니다.

캡처는 폴더를 정리하기 전에 찍어서 실행 명령이 `python .\exp.py`로 보입니다. 정리한 프로젝트에서는 위의 `python .\exploit\exp.py`를 사용하면 됩니다.

![php2shell 로컬 익스플로잇과 www-data 셸 연결 결과](/img/posts/php2shell-shell.png)

*그림 2. 로컬 실습에서 셸 연결 후 `whoami`와 `ls`를 실행한 결과*

스크린샷에 표시되는 메모리 주소와 PID는 실행 때마다 달라질 수 있습니다. 또한 이 화면은 **제가 고정한 PHP 8.2.6 mod_php 디버그 환경에서 얻은 결과**입니다. PHP 8.4.26과 8.4.27의 비교 컨테이너에 같은 익스플로잇을 적용해 성공·실패를 검증했다는 의미는 아닙니다.

## 07_Outro

이번 취약점에서 인상적이었던 부분은 PHP 페이지의 코드가 실행되기 **전**에 문제가 시작된다는 점입니다. 메모리 부족으로 요청을 중단했는데, 그 뒤의 정리 과정이 미완성 상태를 믿고 처리하면서 RCE로 이어졌습니다. 그래서 평범한 웹사이트도 런타임 버전과 실행 환경을 꼭 확인해야 합니다.
