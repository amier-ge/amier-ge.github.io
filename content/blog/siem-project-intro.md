## Intro

안녕하세요! 이번 학기에는 팀원과 함께 **SIEM 기반 보안 사고 탐지 및 대응 지원 플랫폼**을 만들어보려고 합니다.

보안 로그에서 수상한 이벤트를 찾는 것만으로는 사고 분석이 끝나지 않습니다.<br>
왜 탐지됐는지, 앞뒤에 어떤 행위가 있었는지, 실제 침해로 볼 수 있는지를 다시 확인해야 합니다.

그래서 저희는 **룰 기반 탐지**와 **Local LLM의 추가 조사**를 하나의 흐름으로 연결해보기로 했습니다.

```text
Windows 로그 → ELK → 룰 기반 탐지 → Local LLM 분석 → 약식 보고서 → 사람의 최종 검토
```

이번 글에서는 프로젝트를 시작하게 된 이유와 전체 구조, 그리고 제가 맡은 부분을 소개하겠습니다!

## 00_프로젝트 목표

목표는 Windows 환경에서 발생한 의심 행위를 찾고, 보안 담당자가 바로 검토할 수 있는 **침해사고 의심 보고서**로 정리하는 것입니다.

여기서 ‘대응’은 PC를 자동으로 격리하거나 파일을 삭제한다는 뜻은 아닙니다. 로그를 근거로 사고 가능성을 판단하고, 사람이 빠르게 다음 조치를 선택할 수 있도록 돕는 단계까지를 의미합니다.

프로젝트에서 풀고 싶은 문제는 크게 세 가지입니다.

1. 수많은 로그 중에서 조사할 이벤트를 어떻게 먼저 고를 것인가?
2. 탐지된 이벤트 주변의 관련 로그를 어떻게 자동으로 수집할 것인가?
3. 수집한 로그를 어떤 근거로 정상 또는 침해 의심으로 판단할 것인가?

단순히 LLM에게 로그 한 줄을 보여주고 ‘악성인가요?’라고 묻는 방식은 피하려고 합니다. 모델이 실제 ELK를 조회하고, 확인한 로그를 근거로 결론을 내리도록 만드는 것이 핵심입니다.
<br><br>

## 01_왜 룰과 LLM을 함께 사용하는가

Sigma와 같은 탐지 룰은 조건이 명확하고 빠릅니다. 반면 하나의 이벤트만 보고 판단하기 때문에 정상적인 관리 명령이나 개발 작업도 경고로 잡힐 수 있습니다.

LLM은 여러 로그의 맥락을 문장으로 정리하는 데 유리하지만, 전체 로그를 매번 넘기면 느리고 근거가 흐려질 수 있습니다. 결국 두 방식은 경쟁 관계라기보다 역할이 다릅니다.

| 구성 요소 | 맡는 역할 |
|---|---|
| 탐지 룰 | 전체 로그에서 조사할 후보를 빠르게 선정 |
| Local LLM | 후보 이벤트의 전후 로그를 조회하고 맥락 분석 |
| 보고서 | 판단과 근거를 사람이 확인할 수 있는 형태로 정리 |
| 보안 담당자 | 보고서를 검토하고 실제 대응 여부 결정 |

즉, 룰은 **어디를 볼지** 정하고 LLM은 **주변에서 무슨 일이 있었는지** 설명합니다.

## 02_전체 구조

처음 설계한 흐름은 다음과 같습니다.

![ELK에서 룰 기반 탐지와 로컬 LLM 분석을 거쳐 보고서를 작성하는 프로젝트 흐름도](/img/posts/siem-project-flow.png)

### 02-1_ELK

Windows Event Log와 Sysmon 로그를 Elasticsearch에 적재하고, Kibana에서 시간·호스트·이벤트 종류별로 조회합니다. 프로세스 실행, 파일 생성, 네트워크 연결처럼 서로 다른 이벤트를 하나의 시간 흐름으로 확인할 수 있어야 합니다.

### 02-2_룰 기반 탐지

SIEM에 들어오는 로그를 탐지 룰로 검사합니다. 룰에 일치한 이벤트는 악성으로 확정하는 것이 아니라, LLM이 확인할 **조사 후보 Alert**가 됩니다.

### 02-3_Local LLM 조사

LLM은 Alert에 포함된 호스트, 시각, 프로세스, 파일 경로 등을 기준으로 ELK에서 관련 로그를 추가 조회합니다. 한 번의 검색으로 결론이 나지 않으면 결과를 분석하고 다음 조회 조건을 다시 선택하도록 구성할 예정입니다.

### 02-4_약식 보고서

마지막에는 사건 요약, 타임라인, 판단 근거, 확인하지 못한 부분을 보고서로 만듭니다. 결론보다 중요한 것은 **어떤 로그를 보고 그렇게 판단했는지** 남기는 것입니다.

## 03_역할 분담

이번 프로젝트는 각자 맡은 영역을 나누어 진행합니다.

저는 **ELK 환경 구축과 데이터 적재, Local LLM 연결, 로그 조회 하네스, 프롬프트 및 보고서 구조**를 맡았습니다. 쉽게 말하면 탐지 Alert가 들어온 뒤, LLM이 실제 로그를 찾아 분석하고 결과를 남기는 뒷부분을 만드는 역할입니다.

팀원은 **Windows 로그 분석과 탐지 시나리오, Sigma·YARA 룰의 조사 및 개발**을 맡습니다. 따라서 이 글에서는 Sigma 룰 자체를 깊게 다루기보다, 팀원이 만든 탐지 결과를 제 분석 파이프라인에 어떤 형태로 전달할지에 초점을 맞추겠습니다.

```text
팀원: Windows 로그 분석 → Sigma·YARA 룰 → Alert
                                      ↓
나:   ELK 환경 → Local LLM 조사 → 분석 보고서
```

두 부분이 잘 동작하더라도 Alert의 필드명이나 시간 기준이 다르면 연결할 수 없습니다. 그래서 프로젝트 초반부터 **Alert 데이터 형식과 공통 로그 필드**도 함께 맞출 계획입니다.

## 04_실험 데이터 구상

실험은 같은 조직에서 여러 Windows PC가 동시에 로그를 보내는 상황을 가정합니다.

초기 구상은 다음과 같습니다.

- 정상 사용자 PC 약 10대
- 침해된 PC 1대
- 동일한 5시간 구간
- 시작 후 약 3시간 뒤 악성 행위 발생
- 정답 데이터는 탐지 입력에서 제외하고 평가할 때만 사용

서로 다른 출처의 정상 로그와 악성 로그를 억지로 합치면 필드와 시간대가 달라질 수 있습니다. 가능하면 같은 네트워크와 같은 수집 방식으로 만들어진 공개 데이터셋을 선택하려고 합니다.

또한 정상 PC에는 브라우저, 메일, 파일 작업처럼 실제 업무 행위가 충분히 들어 있어야 합니다. 그래야 단순히 ‘조용한 PC와 공격 PC’를 구별하는 것이 아니라, 정상적인 잡음 속에서도 사고의 흐름을 찾을 수 있습니다.

## 05_확인할 질문

프로젝트를 진행하면서 아래 질문에 답해보려 합니다.

1. 탐지 룰이 만든 Alert만으로 조사에 필요한 시작점을 충분히 전달할 수 있는가?
2. Local LLM이 필요한 로그를 스스로 조회하면서도 무한 반복에 빠지지 않는가?
3. 정상 사용자 행위와 공격 행위를 어떤 근거로 구분하는가?
4. 보고서의 결론을 원본 로그로 다시 검증할 수 있는가?
5. 로컬 환경의 속도와 자원만으로 실제 관제 흐름을 재현할 수 있는가?

성공한 결과만 보여주기보다 오탐, 미탐, 조회 실패처럼 구조를 바꾸게 만든 과정도 함께 기록할 예정입니다.
