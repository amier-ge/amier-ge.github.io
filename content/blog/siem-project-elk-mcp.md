## Intro

지난 글에서는 룰 기반 탐지와 Local LLM을 연결하는 프로젝트의 전체 구조를 소개했습니다.

이번에는 분석에 사용할 **DEDALE 데이터셋**을 정하고, 실제 Windows 로그를 Elasticsearch에 넣었습니다. 이후 Qwen이 사람 대신 Elasticsearch를 조회할 수 있도록 MCP도 연결했습니다.

```text
DEDALE 원본 로그 → Elasticsearch → Kibana
                              ↘ MCP → Qwen
```

환경을 만들면서 가장 중요했던 것은 ‘로그가 들어갔다’가 아니라, **정답을 보지 않은 모델이 필요한 로그만 다시 찾을 수 있는가**였습니다.
<br><br>

## 00_왜 DEDALE을 선택했는가

처음에는 정상 로그와 악성 로그를 서로 다른 데이터셋에서 가져오는 방법도 생각했습니다. 하지만 수집 형식, 호스트 이름, 시간대가 다르면 탐지 성능보다 데이터 변환의 영향을 더 크게 받게 됩니다.

DEDALE은 하나의 모의 기업망에서 정상 사용자 활동과 공격 시나리오를 함께 생성합니다. Windows 업무 PC에는 웹 탐색, 이메일, 파일 생성·수정·복사, VPN 같은 정상 행위가 포함되어 있고, 공격 기간의 로그도 같은 방식으로 수집됩니다.

즉, 정상 로그와 악성 로그를 억지로 섞지 않고 **같은 조직에서 발생한 것처럼 구성할 수 있다**는 점이 가장 좋았습니다.

이번 프로젝트에서 사용한 자료는 세 종류입니다.

| 자료 | 사용 목적 |
|---|---|
| Winlogbeat 원본 | Elasticsearch에 넣는 실제 탐지 입력 |
| System Log Labels | 악성·관련·정상 이벤트를 구분하는 평가용 정답 |
| User Behaviour Log | 정상 사용자의 실제 작업과 오탐 원인 확인 |

여기서 Labels는 LLM에게 주지 않습니다. 분석이 끝난 뒤 결과를 비교할 때만 사용해야 **정답을 미리 본 탐지**가 되지 않기 때문입니다.

## 01_로그 파일 확인

Winlogbeat 원본을 풀어보면 아래처럼 시간별 파일이 많이 나옵니다.

```text
D1_H0_2024-12-23T00_winlogbeat_F1.jsonl.bz2
D3_H19_2024-12-25T19_winlogbeat_F68.jsonl.bz2
...
```

파일명에는 데이터 구간, 시간, 수집기, 순번이 들어갑니다. 내부 형식은 한 줄에 JSON 객체 하나를 저장한 **JSONL**이고, 용량을 줄이기 위해 bzip2로 압축되어 있습니다.

```text
.jsonl.bz2
  └─ bzip2 압축
      └─ JSON Lines
          ├─ 이벤트 1
          ├─ 이벤트 2
          └─ 이벤트 3 ...
```

일반 편집기에서 바로 열리지 않았던 이유도 여기에 있었습니다. 먼저 압축을 풀어야 하고, 파일이 크면 편집기가 전체 내용을 한 번에 읽지 못할 수도 있습니다.

또 일부 파일은 압축 상태에서 약 14바이트뿐이었습니다. 압축을 풀어도 비어 있었는데, 다운로드 오류가 아니라 **해당 시간대에 저장된 이벤트가 없는 빈 파일**이었습니다. 크기와 압축 무결성을 함께 확인하고 나서야 데이터 자체의 특성이라는 것을 알 수 있었습니다.

## 02_6대 PC와 5시간 구간 선정

초기 계획은 정상 PC 10대와 침해 PC 1대였지만, 반복 실험과 로컬 분석 시간을 고려해 **정상 5대 + 침해 1대**로 범위를 줄였습니다. 호스트 수를 줄여도 여러 정상 사용자가 섞인 환경은 유지할 수 있고, 쿼리와 LLM 분석을 더 자주 검증할 수 있기 때문입니다.

최종 구간은 다음과 같습니다.

| 구분 | 선택 값 |
|---|---|
| 시간 | 2025-01-06 09:00:00 ~ 14:00:00 UTC |
| 정상 PC | CLIENT3, CLIENT7, CLIENT8, CLIENT14, CLIENT29 |
| 침해 PC | CLIENT2 |
| 전체 이벤트 | 878,146건 |
| 악성 시작 | 10:01:05 UTC |
| CLIENT2 정답 이벤트 | 악성 및 공격 관련 432건 |

다섯 시간 중 약 한 시간이 지난 뒤 공격이 시작됩니다. 앞부분에는 정상 상태의 로그가 있고, 이후에는 공격과 정상 행위가 함께 섞입니다.

호스트는 단순히 로그가 많은 순서로 고르지 않았습니다. 같은 구간에 실제 이벤트가 존재하는지 확인하고, Labels에서 침해 대상으로 표시되지 않은 서로 다른 Windows PC를 정상 호스트로 선정했습니다.

## 03_ELK 구성

서버에는 Elasticsearch와 Kibana 8.19.23을 구성했습니다.

이번 데이터는 이미 수집이 끝난 과거 JSONL 파일입니다. 따라서 실시간 Winlogbeat 수집이나 Logstash 파이프라인을 새로 두지 않고, Python 적재 도구로 Elasticsearch Bulk API에 직접 넣었습니다.

```text
시간별 JSONL.BZ2
  → 압축 해제 및 한 줄씩 읽기
  → 선택한 시간·호스트만 필터링
  → Elasticsearch Bulk 적재
  → Kibana Data View 연결
```

데이터는 전용 인덱스로 분리했습니다.

```text
dedale-winlogbeat-6pc-5h-20250106
```

인덱스 이름에 데이터셋, 호스트 수, 시간 길이, 날짜를 넣어두면 다른 실험 로그와 섞이는 일을 줄일 수 있습니다. Kibana Data View도 같은 인덱스만 바라보도록 만들었습니다.

Kibana의 Discover에서는 `@timestamp`, `host.name`, `event.code`를 기준으로 로그를 확인했습니다. 특히 시간 필터가 브라우저의 현재 시각으로 설정되어 있으면 과거 로그가 보이지 않으므로, 반드시 2025년 실험 구간을 지정해야 했습니다.

```text
Kibana → Discover
Data View → dedale-winlogbeat-6pc-5h-20250106
Time Range → 2025-01-06 09:00 ~ 14:00 UTC
```

이 단계에서 여섯 호스트와 878,146건의 문서가 모두 들어간 것을 확인했습니다.

## 04_Qwen과 Elasticsearch MCP 연결

다음 목표는 Local LLM이 Elasticsearch를 직접 조회하도록 만드는 것이었습니다.

모델은 Ollama의 `qwen3.6:27b`를 사용했고, Elasticsearch 조회 도구는 Elastic에서 공개한 MCP Server를 연결했습니다. MCP는 모델이 정해진 도구의 설명을 읽고, 필요한 인자와 함께 호출할 수 있게 해주는 연결 규격입니다.

```text
사용자 또는 Alert
      ↓
Qwen 3.6 27B
      ↓ 도구 호출
Elasticsearch MCP Server
      ↓ 읽기 전용 검색
Elasticsearch
```

여기서 중요한 점이 하나 있습니다. 터미널에서 `ollama run qwen3.6:27b`를 실행했다고 해서 MCP가 자동으로 연결되는 것은 아닙니다. 모델의 응답과 도구 호출을 중간에서 이어주는 **클라이언트 또는 하네스**가 필요합니다.

그래서 서버에 작은 Bridge와 웹 GUI를 구성했습니다. 사용자는 GUI에서 질문하고, Bridge는 모델이 요청한 Elasticsearch 도구를 실행한 뒤 그 결과를 다시 모델에 전달합니다.

Elasticsearch 권한은 읽기 전용 API Key로 제한했습니다. LLM이 실수로 인덱스를 삭제하거나 문서를 수정할 필요가 없기 때문입니다.

| 항목 | 설정 |
|---|---|
| 모델 | Ollama `qwen3.6:27b` |
| MCP Server | Elastic Elasticsearch MCP v0.4.6 |
| 접근 범위 | 로그 검색 및 인덱스 정보 확인 |
| Elasticsearch 권한 | Read Only |
| 접속 방식 | SSH Tunnel을 통한 로컬 브라우저 GUI |

서버의 웹 포트를 외부에 그대로 공개하지 않고 SSH Tunnel로 내 PC에 전달했습니다. 덕분에 서버는 원격에 있지만 브라우저에서는 로컬 주소처럼 접속할 수 있습니다.

## 05_연결 검증

‘연결 완료’라는 문구만 보고 끝내면 실제로 모델이 도구를 사용했는지 알 수 없습니다. 그래서 다음 순서로 확인했습니다.

1. 모델이 Elasticsearch 인덱스 목록을 조회하는가?
2. 지정한 DEDALE 인덱스를 찾는가?
3. 호스트별 문서 수를 집계하는가?
4. 특정 시간대의 Sysmon 이벤트를 검색하는가?
5. 반환된 필드만 사용해 답변하는가?

처음에는 시험용 인덱스의 소량 로그로 연결을 확인했고, 이후 실제 6대·5시간 인덱스로 교체했습니다. GUI에서 문서 수와 호스트 이름을 물었을 때 MCP 호출 기록과 Elasticsearch 결과가 함께 남는 것을 확인했습니다.

이로써 아래 구간까지 준비됐습니다.

```text
[완료] DEDALE 로그 선정
[완료] Elasticsearch 적재
[완료] Kibana 조회
[완료] Qwen ↔ MCP ↔ Elasticsearch 검색
[다음] Sigma Alert를 입력으로 받아 자동 조사
```

## 06_진행하면서 배운 점

가장 시간이 많이 든 부분은 프로그램 설치보다 **데이터의 경계를 정확히 정하는 일**이었습니다.

- 빈 압축 파일은 오류가 아니라 이벤트가 없는 시간대일 수 있습니다.
- Labels는 탐지 입력이 아니라 평가 기준으로 분리해야 합니다.
- Kibana에서 과거 로그가 안 보이면 먼저 시간 범위를 확인해야 합니다.
- MCP Server만 설치해도 모델과 자동 연결되는 것은 아닙니다.
- 모델의 Elasticsearch 권한은 분석 목적에 맞게 읽기 전용으로 제한하는 것이 안전합니다.

결국 환경 구축은 서비스를 실행하는 것으로 끝나지 않았습니다. 어떤 로그가 들어갔고, 모델이 무엇을 볼 수 있으며, 결과를 어떻게 다시 검증할지까지 정해야 하나의 실험 환경이 됐습니다.
